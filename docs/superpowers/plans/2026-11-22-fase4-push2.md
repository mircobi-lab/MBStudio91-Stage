**Goal:** Il Push 2 affianca la Launchpad come seconda superficie di controllo: 64 pad RGB per le patch del banco, pulsanti sopra il display per i banchi, pulsanti sotto per mute e navigazione, encoder sui volumi, tap tempo, PANIC, e il display da 960x160 con nome patch, quattro postazioni, banco e BPM in stile MBStudio91.

**Architecture:** `Push2Mapping` (pura, testata) traduce note e CC in `SurfaceAction` e lo `SurfaceState` in messaggi LED, esattamente come `LaunchpadMapping`. `Push2Controller` implementa `ControlSurface`, apre la User Port, entra in User mode e gestisce il collegamento a caldo. Il display è separato (`Push2Display`): disegna in un `juce::Image` con lo stesso look dei plugin MBStudio91, poi converte in RGB565 e lo manda via USB bulk. Le due superfici convivono: il `SurfaceCoordinator` esiste già e manda lo stesso stato a tutte.

**Tech Stack:** C++17, JUCE 8.0.15, libusb (via CMake FetchContent), CMake, GitHub Actions `macos-15-intel`, `juce::UnitTest`.

**Spec:** `docs/superpowers/specs/2026-11-21-mbstudio91-stage-design.md` (5.4, superficie di controllo) e la specifica ufficiale Ableton (vedi Fonte sotto).

## Fonte dei dati del protocollo

Tutti i numeri qui sotto vengono dal manuale ufficiale *Ableton Push 2 MIDI and Display Interface*, pubblicato da Ableton su GitHub (`Ableton/push-interface`), letto il 22 novembre 2026. Nessun valore è stato ricordato a memoria. Quelli marcati **[da verificare]** vanno controllati sul Push 2 di Mirco prima di considerarli definitivi.

### MIDI

| Cosa | Valore |
|---|---|
| Porta da usare | "Ableton Push 2 User Port" (la Live Port è di Ableton Live) |
| Entrare in User mode | sysex `F0 00 21 1D 01 01 0A 01 F7` (Set MIDI Mode, 1 = User) |
| Tornare a Live mode all'uscita | stesso comando con argomento `00` |
| Pad | note 36-99; in basso a sinistra 36, in basso a destra 43, in alto a destra 99; `nota = 36 + 8*riga + colonna` con riga 0 in basso **[da verificare: il manuale rimanda a una figura]** |
| Colore di un pad | note-on `90 <nota> <indice tavolozza>`; canale 0 = nessuna animazione, canali 1-15 = animazioni |
| Tavolozza predefinita | 0 nero, 122 bianco, 123 grigio chiaro, 124 grigio scuro, 125 blu, 126 verde, 127 rosso |
| Ambra | non elencata nel manuale. **Decisione: non si usa.** Il Push 2 ha i colori pieni, quindi la patch salvata e' blu (125) invece che ambra come sulla Launchpad. Cosi' si usano solo indici documentati e non si inventa il formato di Set LED Color Palette Entry. |
| Pulsanti sopra il display | CC 102-109 |
| Pulsanti sotto il display | CC 20-27 |
| Scene (destra) | CC 36 (scene 8) ... CC 43 (scene 1) |
| Tap tempo | CC 3; metronomo CC 9 |
| Play 85, Record 86, Stop Clip 29, Master 28, Setup 30, Layout 31, Shift 49, User 59, Mute 60, Solo 61 | |
| Encoder | CC 71-78 (sopra il display), master volume 79, tempo 14, swing 15 |
| Valore encoder | relativo a 7 bit in complemento a due: 1-63 verso destra, 127-64 verso sinistra (127 = uno scatto a sinistra); giro completo circa 210 scatti |
| Tocco encoder | note-on sul numero di nota dell'encoder, velocity 127 premuto / 0 rilasciato |
| Luminosità LED | limitata a 8 quando il Push 2 è alimentato solo da USB |

### Display

| Cosa | Valore |
|---|---|
| USB | vendor `0x2982`, product `0x1967`, interfaccia 0, endpoint bulk OUT `0x01` |
| Risoluzione | 960 x 160, prima riga in alto, primo pixel a sinistra |
| Pixel | 16 bit little-endian RGB565: bit 15-11 blu, 10-5 verde, 4-0 rosso (attenzione: blu e rosso sono invertiti rispetto al solito) |
| Riga | 2048 byte: 1920 di pixel + 128 di riempimento (valore non specificato dal manuale) **[da verificare]** |
| Intestazione frame | 16 byte: `FF CC AA 88` seguiti da dodici `00`, prima dei pixel |
| XOR | i dati pixel vanno messi in XOR con il motivo ripetuto `E7 F3 E7 FF` |
| Frame | 640 buffer da 512 byte; 60 fps; il display diventa nero dopo 2 secondi senza frame |

## Global Constraints

- Vincoli delle fasi 1-3 invariati (x86_64, macOS 12+, build solo su Actions, nessun caricamento sul thread audio).
- Launchpad e Push 2 funzionano insieme: entrambe sono `ControlSurface` registrate nel `SurfaceCoordinator`, che già manda lo stesso stato a tutte.
- L'assenza del Push 2 non deve dare errori né rallentare l'avvio.
- All'uscita l'app spegne i LED e rimette il Push 2 in Live mode, così Ableton lo ritrova com'era.
- Il display usa lo stile MBStudio91 (skill `mbstudio-hardware-ui`): fondo nero, scritte bianche Bebas Neue, accenti verde LED e rosso PANIC.
- Il display si ridisegna solo quando cambia qualcosa, al massimo 30 fps, e manda comunque un frame almeno ogni secondo (altrimenti si spegne da solo dopo 2 s).
- Il Push 2 non deve mai suonare le postazioni: i suoi pad sono comandi, non note. `StageEngine::isReservedControlDevice` va esteso.

## Review Focus

1. **Push 2 collegato dopo l'avvio, o staccato durante l'uso**: si aggancia e si sgancia senza crash, i LED tornano giusti. → Task 2 e 4.
2. **Ableton Live aperto insieme a Stage**: Stage usa solo la User Port e non ruba il Push 2 a Live. → verifica manuale nel collaudo.
3. **Encoder girato velocemente**: il valore relativo in complemento a due non deve mai saltare dal minimo al massimo (un giro a sinistra letto come +127). → Task 1.
4. **Display che non riceve frame**: dopo 2 s si spegne; il controller deve rinfrescare anche quando nulla cambia. → Task 3.
5. **USB non disponibile** (permessi, libusb assente, Push 2 occupato da Live): i pad e i pulsanti continuano a funzionare, solo il display resta spento. → Task 3.

### Task 1: Push2Mapping

**Interfaces — Produces:**
```cpp
namespace Push2Mapping {
    SurfaceAction decode (const juce::MidiMessage&);
    int encoderDelta (const juce::MidiMessage&);          // 1..63 destra, -1..-64 sinistra, 0 se non e' un encoder
    int encoderIndex (const juce::MidiMessage&);          // 0..7 encoder sopra il display, 8 master, -1 altro
    enum class Colour { off, white, lightGrey, darkGrey, blue, green, red };
    int paletteIndex (Colour);                            // solo indici documentati da Ableton
    std::vector<juce::MidiMessage> ledMessages (const SurfaceState&, const SurfaceState* previous);
    std::vector<juce::MidiMessage> initMessages();        // User mode
    std::vector<juce::MidiMessage> shutdownMessages();    // LED spenti + Live mode
}
```
Mappa delle azioni **[proposta]**: pad 36-99 → `patch` 0-63 (indice 0 in alto a sinistra, come sullo schermo e sulla Launchpad, quindi `indice = 63 - 8*riga_dal_basso + ... ` da calcolare in modo che il pad in alto a sinistra sia la patch 1); CC 102-109 → `bank` 0-7; CC 20-23 → `mute` 0-3; CC 24 → `previous`; CC 25 → `next`; CC 3 (tap tempo) → `tap`; CC 29 (stop clip) → `panicDown`/`panicUp`; encoder 71-74 → volume postazioni 1-4, encoder 79 → master, encoder 14 → BPM.

### Task 2: Push2Controller

**Interfaces — Produces:** `class Push2Controller final : public ControlSurface` con la stessa forma di `LaunchpadController`: apre il primo ingresso e la prima uscita MIDI il cui nome contiene "Push 2" e "User", manda `initMessages()`, aggiorna i LED a 20 Hz solo se cambiati, trasforma la pressione lunga di PANIC (500 ms) in `panic`, si riaggancia al cambio dei dispositivi, e all'uscita manda `shutdownMessages()`.
- Gli encoder diventano azioni nuove: `SurfaceActionType::stationVolume` (index = postazione, delta in un campo nuovo `delta`), `masterVolume`, `tempoDelta`. `ControlSurface.h` cresce di un campo `int delta = 0;` in `SurfaceAction`.
- `SurfaceCoordinator` le gestisce: volume postazione `+= delta * 0.5 dB` limitato a -60..+6, master uguale, BPM `+= delta` solo in tempo libero.
- Test: come per la Launchpad, la pressione lunga di PANIC con orologio finto; nel coordinatore, encoder che alza e abbassa il volume e si ferma ai limiti.
- **Commit** `feat: Push 2 come seconda superficie di controllo`

### Task 3: Push2Display

**Interfaces — Produces:**
```cpp
namespace Push2Pixels {
    static constexpr int width = 960, height = 160, lineBytes = 2048, pixelBytes = 1920;
    uint16_t toRgb565 (juce::Colour);                                  // bit 15-11 blu, 10-5 verde, 4-0 rosso
    void encodeFrame (const juce::Image&, std::vector<uint8_t>& out);  // 160 righe x 2048 byte, XOR E7 F3 E7 FF
    const std::array<uint8_t, 16>& frameHeader();
}
class Push2Display : private juce::Timer {
public:
    bool isConnected() const;          // false se libusb manca o il Push 2 non risponde
    void showState (const SurfaceState&);
    juce::String lastError() const;
};
```
- Il disegno avviene in un `juce::Image` 960x160 ARGB: in alto il nome della patch con banco e numero, a sinistra il BPM con INT/EXT, le quattro postazioni in colonne con nome dello strumento e barra del volume, i mute in rosso, il LED verde di ogni tastiera collegata.
- La parte USB vive dietro `isConnected()`: se libusb non si carica o il dispositivo non si apre, l'errore finisce in `lastError()` e tutto il resto continua a funzionare (Review Focus 5).
- **[decisione aperta]** libusb entra come dipendenza CMake (`libusb/libusb-cmake` via FetchContent, che compila su macOS senza autotools). Se non compila su Actions, l'alternativa è parlare direttamente con IOKit, più codice ma senza dipendenze. Da provare in CI prima di scrivere il disegno.
- Test (senza hardware): `toRgb565` su nero, bianco, rosso puro, verde puro, blu puro con i bit nelle posizioni giuste; `encodeFrame` produce 160*2048 byte, la prima riga ha i primi 1920 byte di pixel e 128 di riempimento, e applica lo XOR nel verso giusto (XOR due volte restituisce l'originale); `frameHeader()` comincia con `FF CC AA 88` ed è lunga 16.
